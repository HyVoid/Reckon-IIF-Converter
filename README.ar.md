## ما يساعدك على تتبعه

* سجلات فواتير CRM التي لا يمكن استيرادها إلى Reckon قبل أن تتسبب في أخطاء محاسبية.
* عدم تطابق تعيينات العملاء ورموز الضرائب والعناصر والحسابات بين الأنظمة.
* حالة جهوزية استيراد دفعات الفواتير ومخاطر فشل الاستيراد.
* الفواتير المكررة والبيانات الرئيسية المحاسبية المفقودة.
* معدل معالجة الفواتير ونسب الاستثناءات ونسب نجاح التحقق.
* القيمة الإجمالية للفواتير المُعدّة للترحيل المالي في دفعة واحدة.

## لماذا بنيت هذا

تفترض معظم الشركات أن مشكلتها هي "إنشاء ملف IIF".

في الواقع، المشكلة الحقيقية مختلفة.

يحدث الفشل التشغيلي لأن معلومات الفواتير موجودة أصلًا داخل CRM، لكن على فرق المالية إعادة إنشاء المعلومات نفسها يدويًا داخل برنامج المحاسبة. كل فاتورة تتطلب إعادة كتابة العملاء والمنتجات ورموز الضرائب والحسابات والمبالغ. ومع نمو حجم الفواتير، يتوسع الجهد المحاسبي تقريبًا بشكل خطي.

الفشل الثاني أكثر دقة: غالبًا ما تكتشف الشركات أخطاء الاستيراد فقط بعد محاولة تحميل البيانات إلى نظام المحاسبة. في تلك المرحلة، يجب على المحاسبين التحقيق لمعرفة أي عميل أو رمز ضريبة أو حساب أو تاريخ تسبب في الفشل.

بنيت هذه الأداة لأنني لاحظت مرارًا النمط نفسه:

```text
CRM Export
     ↓
Manual Cleanup
     ↓
Manual Mapping
     ↓
Import Attempt
     ↓
Import Failure
     ↓
Manual Investigation
     ↓
Repeat
```

المشكلة ليست في برنامج المحاسبة. المشكلة هي طبقة الترجمة المفقودة بين الأنظمة التشغيلية والأنظمة المالية.

على سبيل المثال:

### قبل

يحتوي تصدير CRM على:

| العميل | المنتج   | الضريبة | المبلغ |
| ------ | --------- | ------- | ------ |
| ABC Pty | Service A | VAT | $1,500 |

يتوقع Reckon:

| العميل    | العنصر   | رمز الضريبة | الحساب |
| --------- | ------- | --------- | ------- |
| ABC PTY LTD | SERV001 | GST | 4-1000 |

يفشل الاستيراد لأن الهياكل غير متوافقة.

### بعد

يقوم المصنف تلقائيًا بـ:

* تعيين أسماء العملاء،
* ترجمة رموز المنتجات،
* التحقق من رموز الضرائب،
* التحقق من تعيينات الحسابات،
* توليد هياكل معاملات IIF صالحة.

بدلًا من بناء جدول بيانات لمرة واحدة، كان الهدف هو تطوير إطار استدلالي قابل للتكرار:

> "How can operational invoice data be transformed into accounting-compliant transaction data with minimal human intervention?"

### ثلاثة فخاخ تصطاد حتى فرق المالية ذات الخبرة

#### الفخ 1 — افتراض أن أسماء العملاء هي معرّفات

تقوم فريق مالية باستيراد الفواتير باستخدام أسماء عرض العملاء.

الافتراض:

```text
CRM Customer = Accounting Customer
```

الواقع:

| CRM     | Reckon      |
| ------- | ----------- |
| ABC Pty | ABC PTY LTD |
| XYZ Ltd | XYZ LIMITED |

النتيجة:

```text
Import Failure Rate: 18%
```

خطأ الاستدلال هو افتراض أن العناوين هي معرّفات.

النهج الصحيح:

```text
CRM Customer
      ↓
Customer Mapping Table
      ↓
Reckon Customer ID
```

النتيجة الصحيحة:

```text
Import Failure Rate: <1%
```

<details>
<summary>منطق الصيغة</summary>

```excel
=XLOOKUP(
    CRM_Customer,
    Customer_Map[CRM],
    Customer_Map[Reckon],
    "ERROR"
)
```

</details>

---

#### الفخ 2 — افتراض أن رموز الضرائب تُترجم تلقائيًا

القرار:

```text
Use CRM tax values directly.
```

افتراض خاطئ:

```text
VAT = GST
```

الواقع:

| ضريبة CRM | ضريبة Reckon |
| --------- | ------------ |
| VAT       | GST          |
| ZERO      | FRE          |
| EXEMPT    | N-T          |

هذا ينتج عنه تقرير ضريبي غير صالح.

النهج الصحيح:

```text
Tax Mapping Table
        ↓
Validation Rules
        ↓
Accounting Tax Code
```

النتيجة الصحيحة:

* توزيع ضريبي متوافق،
* مخاطر أقل لرفض الاستيراد،
* تقارير متسقة.

<details>
<summary>منطق الصيغة</summary>

```excel
=IFERROR(
    XLOOKUP(
        CRM_Tax,
        Tax_Map[CRM],
        Tax_Map[Reckon]
    ),
    "ERROR"
)
```

</details>

---

#### الفخ 3 — التعامل مع صفوف الفواتير كمستندات فواتير

القرار:

```text
Export rows directly.
```

افتراض خاطئ:

```text
1 Row = 1 Invoice
```

الواقع:

```text
Invoice Header
      ↓
Multiple Invoice Lines
      ↓
TRNS/SPL/ENDTRNS Structure
```

بدون إعادة الهيكلة:

```text
Import Failure
```

النهج الصحيح:

```text
Invoice Grouping
       ↓
Header Generation
       ↓
Line Generation
       ↓
IIF Assembly
```

النتيجة الصحيحة:

```text
100% Reckon-compatible transaction structures
```

<details>
<summary>منطق الصيغة</summary>

```excel
=COUNTIFS(
    InvoiceNo,
    CurrentInvoice
)
```

</details>

### مثال تطبيقي

تصدّر شركة 350 فاتورة من نظام CRM الخاص بها.

التصدير الخام:

| الفاتورة | العميل | المنتج   | الضريبة | المبلغ |
| ------- | ------ | --------- | ------- | ------ |
| INV1001 | ABC Pty | Service A | VAT | 1500 |
| INV1001 | ABC Pty | Service B | VAT | 700 |

يقوم المصنف بتنفيذ:

#### الخطوة 1 — التحقق من العميل

```text
ABC Pty
    ↓
ABC PTY LTD
```

#### الخطوة 2 — تعيين المنتج

```text
Service A
      ↓
SERV001

Service B
      ↓
SERV002
```

#### الخطوة 3 — ترجمة الضريبة

```text
VAT
 ↓
GST
```

#### الخطوة 4 — بناء المعاملة

```text
TRNS
SPL
SPL
ENDTRNS
```

النتيجة النهائية:

| المقياس       | القيمة       |
| ------------- | ----------- |
| الفواتير      | 350         |
| القيمة الإجمالية   | AUD 486,000 |
| الأخطاء        | 7           |
| التحذيرات      | 13          |
| نسبة النجاح  | 98.0%       |

الأثر التشغيلي:

بدلًا من إعادة بناء 350 فاتورة يدويًا داخل Reckon، يعمل موظفو المالية على حل الاستثناءات العشرين المحددة فقط.
